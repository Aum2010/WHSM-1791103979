## 2. สิ่งที่แก้ฝั่งเรา

**ความปลอดภัย**
- `SEC-PD-USERS` + `SEC-PD-PIN-HINTS`: Processing ฝัง PIN จริงของ PD002 / PD004 / PD007 ในตาราง `systemUsers` และในคำอธิบายบล็อก → ลบ · `PD-LOGIN-NO-EMPTY` กันรหัสว่างผ่านการตรวจของหน้าจอ
- `SEC-DCC-SEED`: DCC ฝังบัญชี QA001 / QA002 / Tom พร้อม `SHA-256(salt:รหัส)` ครั้งเดียว (รหัส 4 หลักถอดได้ทันที) → `SEED = []`
- `import-ui.mjs` เก็บ PIN จาก `systemUsers` ไปตรวจซ้ำด้วย · `assertNoSecrets` เพิ่ม 2 แบบ (systemUsers มีรหัส / hash ใน DCC)
- เอกสารสรุป BD02 ของลูกค้า (ไฟล์ `75% BD02.html`) เขียนรหัสของ BD001–003 ไว้ · โฟลเดอร์ลูกค้าอยู่ใน `.gitignore` · ห้ามส่งต่อไฟล์นี้

**ผู้ใช้กลาง (คำตอบลูกค้า ข้อ 2 / ข)**
- ส่วนใหม่ **DCC** (`MODULES`, migration `009_dcc_module.sql`): ผู้ใช้ที่มีสิทธิ์ QA ได้ DCC ระดับเดียวกัน แต่อนุมัติ → ใช้งาน · ผู้ดูแล = ADMIN · template QA = ใช้งาน · ผู้บริหาร / หัวหน้าโรงงาน = ดู
- `GET /auth/module-users?module=X` รายชื่อผู้มีสิทธิ์ส่วนนั้น (ไม่มีรหัส) · เรียกได้เมื่อมีสิทธิ์ส่วนนั้นอย่างน้อย "ดู"
- DCC (bridge + `DCC-VERIFY-SERVER`, `DCC-APPROVER-SERVER`): ทะเบียน `whrm_dcc_users_v1` = รายชื่อจาก server · ADMIN → ผู้ดูแล + ผู้อนุมัติ · APPROVE → ผู้อนุมัติ · รหัสตรวจ `/auth/verify` (DCC) · สร้างผู้ใช้ / รหัส / เปิด-ปิด / ปลดล็อกใน DCC ถูกปิด (ไปทำที่หน้า User) · ตำแหน่ง (titles) และหน่วยงานยังตั้งใน DCC ได้ · หน้า QA_DCC_02 ใช้สิทธิ์ส่วน DCC แทน QA
- ฝ่ายผลิต (bridge): Processing ดักช่อง login / ยืนยันตัวตนแบบเดียวกับ WH13 · ตรวจที่ server ส่วน **ผลิต** ระดับใช้งานขึ้นไป · กลุ่มสิทธิ์: ผู้ดูแล = ADMIN · อนุมัติ = PD supervisor · ใช้งาน = ผู้ปฏิบัติงาน (ปลดล็อก / แก้ / ลบไม่ได้) · รหัสบัตร หรือ "ชื่อในหน้าจอ" = PD002 / PD004 / PD007 → ใช้กลุ่มของบัญชีนั้นในหน้า

**ข้อมูลเก็บที่ server กลาง (คำตอบลูกค้า)** — sync ผ่าน `/sync/kv` (`kv_store`) · `SHARED_KEYS` ใน bridge และ `routes/sync.js` ต้องตรงกัน
- BD02 (อ่าน / เขียนเฉพาะสิทธิ์ BD02 — `access.js`): `pmp_bd_salespeople_v1`, `pmp_bd_sales_targets_v1`, `pmp_bd_sales_zone_assignments_v1`, `whrm_bd_price_history_v1`
- LG02: `lg_pod_v1` (อ่าน LOGISTICS / WH13 · เขียน LOGISTICS)

**กันยอดระหว่างขนส่ง (คำตอบลูกค้า ข้อ ก)** — `LG02-TRF-CHECK-SOURCE` + `LG02-TRF-RESERVE-ON-SAVE`
- ใบโหมด Logistic ที่รถออกแล้วและยังไม่ปิด (`IN_LOGISTIC`, `PARTIAL_RECEIVED`, `WAIT_RECEIVER`, `LOCKED`) → แถว Stock Card ต้นทาง `transactionProcess: 'TRANSIT_RESERVE'` (OUT = ยอดที่ยังไม่รับ · `transactionId` = แผนตัดเดิม + `-RSV`) · ทุกหน้าจอที่คำนวณยอดจาก Stock Card จึงเห็นยอดลดลงทันที

- `__trfRsvReconcile()` ทำงานหลังบันทึกใบโอนทุกครั้งใน LG02 + ทุก 15 วิ ขณะเปิด LG02 · ตรวจยอดต้นทางตอนรับบวกยอดที่ใบนั้นกันไว้คืน
- ข้อจำกัด: WH13 ปิด / ยกเลิกใบ → คืนยอดเมื่อมี LG02 เปิดอยู่สักเครื่อง (ภายใน 15 วิ) · ใบที่รถออกก่อนอัปเดตนี้ ได้แถวกันยอดเมื่อ LG02 เปิดครั้งแรกหลังอัปเดต

## 4. ยังไม่ได้ทำ / ข้อควรทราบ

- **ข้อมูลใหม่เก็บแบบ key-value บน server** (ค่าทั้งก้อนต่อ key) ไม่ใช่ตารางแยกรายใบ — POD ที่มีรูปถ่ายจะโตเร็ว ควรย้ายเป็นเอกสารรายใบ (`doc_store` แบบใบโอน) หรือเก็บรูปเป็นไฟล์
- **VAT:** ใบแจ้งหนี้ / ใบเสร็จของ BD02 คิดแบบรวม VAT ในยอด ไม่ตรงคำตอบลูกค้า (ราคาไม่รวม VAT)
- **ราคาจาก 5 รูป:** ต้องจับคู่ชื่อในรูปกับรหัสสินค้าใน DBV2.0 ก่อนนำเข้า
- **ลบ / export Audit อายุ 1 ปี:** ยังไม่มี
- **DCC:** แผงขวา "Recent DAR activity" และชื่อในมุมขวาบน (วรากร … QA Manager) เป็นข้อความตัวอย่างของลูกค้า · สัญญาณ "หน้าเปิดอยู่" เห็นเฉพาะหน้าที่เปิดบนเครื่องเดียวกัน
- **Pre-order BD02 ↔ PP301** ใช้ BroadcastChannel + localStorage ของลูกค้า — ตอนนี้ข้อมูล sync ข้ามเครื่องแล้ว แต่ยังไม่ได้ทดสอบวงจรเต็ม
- **ไม่นำเข้า:** PR08 (รอขั้นตอนจัดซื้อจริง) · `Production module/Main page/*` (หน้าสำรองของลูกค้า)
- เอกสารสรุปนักพัฒนาของลูกค้าแนะนำให้เขียนระบบใหม่ทั้งชุด (React / NestJS / Keycloak ฯลฯ) — ไม่อยู่ในแผนปัจจุบัน ระบบเรายังใช้หน้าเว็บของลูกค้า + bridge + backend
